Experiment 01

Baseline harness

Before profiling anything, you need a repeatable way to measure. The first step was building a benchmark harness using vLLM's benchmark_serving.py against a resident model loaded in FP16 precision.

Three metrics were defined as the measurement foundation for every subsequent experiment: TTFT (time-to-first-token, which captures prefill latency), ITL (inter-token latency, which captures decode throughput), and end-to-end throughput in tokens per second.

Establishing a clean FP16 baseline first makes every optimization verifiable: any later change can be compared against this reference with no ambiguity about what moved and by how much.
vLLM benchmark_serving.py FP16 TTFT ITL

Experiment 02

Concurrency sweep

With a stable baseline, the next question is: how does the system behave as concurrent load increases? vLLM uses continuous batching, which means incoming requests are packed into active decode batches rather than queued for a fixed batch boundary.

A concurrency sweep from 1 to N simultaneous requests was run while capturing rocprof traces to track compute-unit (CU) occupancy at each load level. The goal was to find the batching knee — the concurrency point where adding more requests stops improving throughput and starts increasing latency.

At low concurrency the GPU is underutilized (CU occupancy well below capacity). Past the knee, occupancy saturates and ITL climbs — the batch is now competing for memory bandwidth rather than idle compute.

Experiment 03

FP8 quantization

Decode throughput on large models is almost always memory-bandwidth bound: each token-generation step loads the full set of model weights from HBM regardless of whether the arithmetic units are busy. Halving weight precision from FP16 to FP8 halves the bytes transferred per step.

The FP16 and FP8 configurations were profiled side-by-side. HBM bandwidth utilization (via rocm-smi and rocprof counters) confirmed that FP16 was hitting the bandwidth ceiling; FP8 moved the same workload well below it, freeing headroom for larger or more concurrent batches.

Accuracy was validated with perplexity on a held-out text corpus to quantify the precision–performance tradeoff and confirm the loss was within acceptable bounds.

FP8 delivered measurably higher throughput and lower ITL on the same hardware, with perplexity degradation small enough to be acceptable for most serving workloads.

Experiment 04

AITER backend

AMD's AITER (AI Tensor Engine for ROCm) is an optional fused-kernel backend for vLLM that replaces several individual GPU kernels with hand-optimized equivalents targeting AMD's compute architecture. The question is whether it helps, hurts, or is neutral for a given model and batch configuration.

The AITER backend was toggled on and off while capturing rocprof kernel traces. Each trace was inspected to identify which kernels were dispatched in each configuration — specifically whether the fused attention and GEMM kernels appeared — and the end-to-end latency difference was measured.

With AITER enabled, fused kernels replaced several sequential dispatches visible in the trace. The reduction in kernel-launch overhead and improved memory access patterns translated to lower TTFT on prefill-heavy workloads.

Experiment 05

Tensor parallelism on a 70B model

A 70B-parameter model does not fit in a single GPU's HBM. Tensor parallelism (TP) shards weight matrices across multiple GPUs so that each device holds only a slice. The cost is an all-reduce communication after every attention and MLP layer, crossing AMD's Infinity Fabric between GPUs.

TP degree was varied (×2, ×4, ×8 where hardware permitted) and throughput was measured at each scale. rocprof traces were used to measure the time spent in all-reduce kernels versus compute kernels, identifying the crossover point where communication overhead consumes enough time to reduce per-GPU efficiency.

Scaling from ×2 to ×4 improved total throughput. Scaling further showed diminishing returns: all-reduce latency across Infinity Fabric became the dominant term, and per-GPU compute utilization fell. The optimal TP degree for this model size was ×4 on the available hardware.

Experiment 06

Roofline analysis

The roofline model plots each kernel on a two-dimensional space: arithmetic intensity (FLOPs per byte transferred) on the x-axis and achieved performance (FLOPs/s) on the y-axis. Two ceilings bound every kernel — the memory bandwidth roof and the compute roof. Where a kernel sits relative to those ceilings tells you exactly which resource limits it and how much headroom remains.

Omniperf was used to generate roofline plots for the key kernels in the vLLM serving pipeline. Attention kernels (especially during decode) appear far left — low arithmetic intensity, memory-bound — while GEMM kernels during prefill appear further right, closer to the compute ceiling.

The roofline confirmed that decode is memory-bandwidth limited (consistent with EXP-03's FP8 result), while large-batch prefill is approaching compute-bound. Optimizations should target these two regimes differently.

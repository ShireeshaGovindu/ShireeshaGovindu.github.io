The KV cache: where inference memory actually goes

A 7B model needs 14 GB for weights. So why does it fall over at batch 16 on a 40 GB card? I went looking for the missing memory.

Shireesha Govindu/ May 2026/ 14 min/ worklog

The first time I tried to serve Llama‑2‑7B myself, the arithmetic looked easy. Weights in fp16 are 7e9 × 2 bytes ≈ 14 GB. I had a 40 GB A100. That leaves 26 GB — surely room for a healthy batch of requests.

It tipped over at batch 16, well short of where the FLOPs ran out. The GPU wasn't compute‑bound; it was out of memory. So the question for this first post is narrow and concrete:

Target

Account for every byte of inference‑time memory on that card, find where it's being wasted, and get the achievable batch size as close to the theoretical maximum as I can — without touching the model.

The short answer is the KV cache: the per‑token attention state we keep around so we don't recompute the whole sequence on every step. The long answer — how big it is, why a naive cache wastes most of itself, and how paging wins it back — is the rest of this post.

01The baseline: a contiguous cache

During generation, attention at step t needs the keys and values of every previous token. Recomputing them each step is quadratic and insane, so we cache them. That cache is the dominant runtime allocation, and its size is fully determined by the model config1:

# bytes of KV state for one token, all layers
kv_per_token = 2 * n_layers * n_kv_heads * head_dim * dtype_bytes
#              ^ K and V

# Llama-2-7B, fp16
kv_per_token = 2 * 32 * 32 * 128 * 2
             = 524288 bytes
             # = 512 KB / token

Half a megabyte per token doesn't sound like much until you multiply by a context window. A single 4096‑token sequence holds 2 GB of KV cache. Our 26 GB of spare memory is really 26 / 2 ≈ 13 full‑length sequences — and that's the ceiling, before any waste. The batch size was never going to be huge.

So far this is just counting. The interesting part is that the 13‑sequence ceiling is wildly optimistic, because a contiguous cache almost never holds 13 sequences' worth of real tokens. It holds 13 sequences' worth of reservations.

02Measuring the waste

The naive implementation does the obvious thing: when a request arrives, reserve one contiguous slab big enough for the longest output it might produce — max_seq_len. You have to, because the tensors are contiguous and you don't know how long generation will run.

That single decision creates three separate leaks:

Reservation waste. A request that asks for up to 2048 tokens but stops after 200 has reserved 2048 and used 200. The other 1848 slots sit allocated and idle for the request's whole lifetime.

Internal fragmentation. Even the reserved slab is rounded up to whatever allocation granularity you chose, so the last partial chunk is dead space.

External fragmentation. Requests come and go with different lengths, leaving contiguous gaps too small to fit the next slab — free memory that can't be used.

I instrumented the naive cache and logged, each step, how many KV bytes held a real token versus how many were merely reserved. On a mixed trace of short and long prompts, steady‑state useful occupancy sat around 35%.2 Two‑thirds of the most precious resource on the card was holding nothing.

This is the whole game. The model is fine. The hardware is fine. We're just managing the memory badly — and it's the exact failure mode that virtual memory solved for operating systems decades ago.

03Iteration one: stop reserving the max

The first fix is the obvious one: don't pre‑reserve max_seq_len. Grow each sequence's allocation as it actually produces tokens.

This kills reservation waste outright — you only ever allocate for tokens that exist. On the same trace, useful occupancy jumped to the ~60% range. A real win, and almost free.

But it trades one problem for another. Growing a contiguous buffer means that when a sequence outgrows its slab you must either over‑allocate again (back to reservation waste) or copy the whole cache to a bigger hole (a bandwidth tax on every growth, exactly when the GPU is busy). And variable‑length slabs coming and going make external fragmentation worse, not better. Occupancy was higher but spiky, and big requests would still fail to find a contiguous home even when total free memory was plenty.

The lesson is that contiguity itself is the enemy. As long as a sequence's cache must be one unbroken run, every allocator trick is just rearranging deck chairs.

04Iteration two: page it

So drop the contiguity requirement. This is the PagedAttention idea3, and it's borrowed wholesale from OS virtual memory.

Carve KV memory into fixed‑size blocks — say 16 tokens each. A sequence no longer owns a slab; it owns a block table, a little list of pointers to however many physical blocks it currently needs. Logically the tokens are sequential; physically the blocks can live anywhere.

# a sequence is now an index, not a slab
block_table[seq_id] = [block_9, block_2, block_41, ...]

# the attention kernel gathers KV through this
# indirection, one block at a time

Three things fall out of this at once:

No external fragmentation. Every block is the same size, so any free block fits any sequence. Free memory is fungible again.

Reservation waste shrinks to one block. The most a sequence can over‑allocate is the unused tail of its last block — at 16 tokens, at most 15 wasted slots, not 1848.

Sharing becomes trivial. Two sequences with a shared prefix (same system prompt, or beam‑search siblings) can point at the same physical blocks until one diverges, then copy‑on‑write a single block. The naive cache couldn't share anything.

The cost is an extra indirection in the hottest kernel: attention now reads KV through the block table instead of striding a contiguous tensor. That's real, and it's why PagedAttention is a custom kernel rather than a memory‑allocator patch — but the overhead is small and the memory it frees buys far more throughput than it costs.4

05Results

Same model, same card, same trace — only the cache changed.

Llama‑2‑7B · A100‑40GB · mixed‑length trace
KV cache Useful occupancy Max batch Rel. throughput
Naive contiguous (reserve max) ~35% 16 1.0×
Grow‑on‑demand contiguous ~60% 27 1.6×
Paged (16‑token blocks) ~96% 44 2.7×

The numbers are illustrative of the shape, not a benchmark you should quote5 — but the shape is the point. Nearly tripling throughput came not from a faster kernel or a smaller model, but from refusing to waste memory. The compute was always there; we just couldn't feed it.

06What I'm taking away

Three things stuck with me, and they'll shape the rest of this series:

At serving time, memory is the budget. Weights are a fixed cost you pay once; the KV cache is the variable cost that decides how many users you can serve at once. Inference optimization is, to a first approximation, KV‑cache optimization.

The bottleneck was management, not capacity. We didn't add memory or shrink the model — we stopped reserving for a worst case that rarely happens. That's a recurring theme in this stack.

Old ideas, new hardware. Paging is fifty years old. Most of what makes modern inference fast is a classic systems idea (virtual memory, batching, speculation, caching) ported onto a GPU's particular constraints. That's encouraging if, like me, your background is systems rather than ML.

Next in the series I'll follow a single block all the way into the attention kernel and watch how PagedAttention actually does the gather on the GPU — where the indirection lands in HBM versus SRAM, and what it costs in bandwidth.

From Prompt to Token: Inside Transformer Inference on AMD GPUs

A practical walkthrough of prefill, decode, attention, KV cache, GPU kernels, and memory bottlenecks in modern LLM inference.

Shireesha Govindu/ June 2026/ 15 min/ worklog

Every time an LLM produces a token, the GPU runs through the same sequence of operations — dozens of kernels firing in order, each consuming and producing tensors, each constrained by a different hardware resource. Knowing which kernel does what, and where it spends its time, is the foundation of any real performance work on AMD ROCm.

This post maps the full path: one transformer layer, every kernel, and what actually shows up when you reach for rocprof or Omniperf.

Goal

Build a mental model precise enough that when a kernel name appears in a profiler trace, you know what operation it corresponds to, what hardware resource it stresses, and whether it should be compute-bound or memory-bound.

00The layer pipeline

A single transformer layer is a fixed sequence. Every token passes through every stage on every forward pass — prefill and decode alike. The structure never changes; only the shapes of the tensors do.

↓

Each stage launches one or more GPU kernels. The rest of this post walks them in order.

01RMSNorm memory-bound

Before the attention block, activations are normalized. Most modern LLMs use RMSNorm rather than LayerNorm — it drops the mean-centering step and is slightly cheaper, but the memory access pattern is the same.

# Operation: normalize each activation vector
x_norm = x / sqrt(mean(x²) + ε) * γ

# Work per call
#  1. Read activations from HBM
#  2. Reduce across hidden dimension (variance)
#  3. Normalize and scale
#  4. Write result back to HBM

Typical kernels you'll see: rmsnorm, fused_rmsnorm. The compute is trivial — a handful of FLOPs per element — so the kernel is almost always memory-bound. Its roofline sits far left on the arithmetic intensity axis.

02QKV Projection GEMM compute-bound

This is where most of the model's floating-point work actually happens. The normalized input is multiplied by a weight matrix to produce queries, keys, and values simultaneously.

# Shape: [batch × seq, hidden] × [hidden, 3 × hidden]
QKV = Input @ W_qkv

# Llama-3-8B example
[batch, 4096] × [4096, 12288]  → [batch, 12288]
#                                  ^ Q | K | V concatenated

Typical kernels: rocblas_gemm, ck_gemm, aiter_gemm. These are the kernels that light up Matrix Cores (MFMA) — AMD's fused-multiply-accumulate units that give MI300X its peak TFLOPS rating. They consume a heavy share of register file and LDS. During prefill, this is often the single most expensive kernel in the layer.

03Q/K/V Split memory-bound

The fused QKV matrix gets sliced into three separate tensors. This is pure memory movement — no arithmetic, just reshaping and permuting to get the right layout for the attention kernel.

split_qkv reshape_qkv permute_qkv

It's lightweight and fast. In profiles it often shows up as a small spike between the big GEMM and the RoPE kernel. Some frameworks fuse it away entirely.

04RoPE lightweight

Rotary Positional Embedding encodes each token's sequence position directly into the Q and K vectors by rotating them in complex space. The result: attention scores naturally decay with distance, without any additive positional table in the weights.

# For each pair of dimensions (d, d+1) in Q and K:
q[d]   = q[d]   * cos(θ) − q[d+1] * sin(θ)
q[d+1] = q[d]   * sin(θ) + q[d+1] * cos(θ)
# Same for k

Typical kernels: rope, fused_rope, rotary_embedding. The operation is cheap — element-wise trig and vector arithmetic — and usually fused into the QKV split or the attention kernel itself. When it shows up separately in a trace it's a short blip.

05KV Cache Write memory-bound

After RoPE, K and V are written into the KV cache so future decode steps can attend to them without recomputation. This kernel exists because we pay a one-time HBM-write cost during prefill to avoid quadratic recompute during decode.

cache_write reshape_and_cache paged_attention_cache

With paged attention, the write goes into non-contiguous physical blocks — the kernel follows a block table rather than striding a flat slab. Fully memory-bound; the cost scales with seq_len × n_kv_heads × head_dim × dtype_bytes per layer.

06Attention memory-bound

This is the most algorithmically interesting kernel in the stack. Mathematically it's three operations chained together:

scores = Q @ Kᵀ / sqrt(head_dim)   # [seq, seq]
weights = softmax(scores)
output  = weights @ V               # [seq, head_dim]

A naïve implementation would materialize the full [seq × seq] score matrix in HBM — a quadratic memory cost that makes long contexts impossible. Modern systems instead use fused kernels that keep the score tile in SRAM and never write it to global memory:

flash_attention paged_attention flash_decode

FlashAttention tiles Q, K, V across SRAM, computing and discarding score tiles on the fly. PagedAttention extends this to non-contiguous KV blocks, reading through a block table. Both kernels are heavily memory-bandwidth limited — the QK and V reads dominate, and the small tiled GEMMs inside sit well below peak MFMA throughput. On MI300X, attention becomes the bottleneck that determines decode throughput.

07Output Projection GEMM compute-bound

The concatenated attention output — all heads stitched back together — is projected back to the model's hidden dimension.

output = attn_output @ W_o
# [batch, n_heads × head_dim] × [n_heads × head_dim, hidden]

Same kernel family as the QKV projection: rocblas_gemm, ck_gemm, or aiter_gemm. Same MFMA-heavy behavior. Compute-bound during prefill; transitions toward memory-bound during single-token decode when the batch dimension is 1.

08MLP Up Projection compute-bound

After the attention block, the residual stream passes through a two-layer MLP. The up-projection expands the hidden dimension — Llama models use a roughly 3.5× expansion.

up   = x @ W_up    # 4096 → 14336
gate = x @ W_gate  # fused in one kernel on some backends

This is one of the largest GEMMs in the model. On a 70B model the up and gate projections together account for more FLOPs than the entire attention block. Profiler traces show it clearly: a long GEMM kernel, high MFMA utilization, high arithmetic intensity.

09SiLU / GELU Activation lightweight

The up-projected output passes through a non-linearity. Llama uses SiLU (Sigmoid Linear Unit); other models use GELU or variants.

SiLU(x) = x * sigmoid(x) = x / (1 + exp(−x))
silu gelu fused_silu

Cheap. Often fused with the gate multiplication below into a single fused_swiglu kernel that reads once and writes once. When it appears standalone in a trace it's a short, memory-bound blip.

10Gate Multiplication lightweight

Llama's MLP uses a gated activation — the SiLU output is multiplied element-wise by a separate gate projection. The gate acts as a learned per-element mask that sharpens or suppresses activations.

output = SiLU(up_proj) * gate_proj
elementwise_mul fused_swiglu

Memory-bound and fast. The fused SwiGLU kernel is the common form: one kernel reads up_proj and gate_proj, applies SiLU to one, multiplies, writes the result. Halves the HBM traffic compared to two separate kernels.

11MLP Down Projection compute-bound

The final step of the MLP block: project back to the model's hidden dimension.

hidden = mlp_output @ W_down   # 14336 → 4096

Another large GEMM, same kernel family as the up projection, same MFMA utilization pattern. The down projection closes the layer; a residual add folds the MLP output back into the main stream and we're ready for the next layer.

12What ROCm Profiler actually shows

When you run rocprof --stats or Omniperf against a Llama inference workload, the top kernel names look roughly like this — exact names vary by framework version and which backend (rocBLAS, CK, AITER) is selected at runtime:

# Common kernel names in a ROCm trace
ck_gemm_kernel                 # QKV, output, MLP projections
aiter_gemm                     # same, if AITER backend is active
rocblas_sgemm / hgemm          # fallback GEMM path
fused_rmsnorm_kernel           # pre-attention normalization
rotary_embedding_kernel        # RoPE
reshape_and_cache_kernel       # KV cache write
flash_attention_fwd            # prefill attention
paged_attention_v1 / v2        # decode attention
fused_swiglu_kernel            # SiLU + gate multiply
elementwise_mul_kernel         # gate multiply (unfused path)

The distribution of time across these kernels is what changes between prefill and decode — same names, very different proportions.

13Prefill vs. decode: the same kernels, different bottlenecks

During prefill, the model processes all prompt tokens in parallel. Sequence lengths are long, batch matrices are large, and the GEMMs are fat and square — ideal for MFMA units. The profile looks like a long series of compute-bound GEMM kernels, one stack per transformer layer:

# Prefill — 32-layer model, dominant kernels in order
for layer in range(32):
    rmsnorm           # cheap
    gemm_qkv          # large, compute-bound ←
    rope              # cheap
    flash_attention   # grows quadratically with seq_len ←
    gemm_output       # compute-bound ←
    gemm_up / gate    # largest GEMM ←
    fused_swiglu      # cheap
    gemm_down         # compute-bound ←

During decode, one new token is generated per step. The GEMM shapes collapse: the sequence-length dimension becomes 1, turning large matrix multiplications into matrix-vector products — a form that barely touches the MFMA units and is almost entirely memory-bandwidth limited. Meanwhile, the attention kernel must read the full KV cache — which grows with every generated token.

# Decode — dominant shift in kernel cost
for layer in range(32):
    rmsnorm            # cheap
    gemm_q             # now tiny: [1, hidden] × [hidden, head_dim]
    rope               # cheap
    paged_attention    # reads full KV cache, memory-bound ←←
    gemm_output        # tiny matrix-vector
    gemm_up / gate     # also memory-bound now
    fused_swiglu
    gemm_down          # memory-bound

This is why decode throughput on a GPU like MI300X or H100 is gated by HBM memory bandwidth, not compute. The weights are read from HBM on every token step for every layer; the KV cache is also read in full on every step. The GEMMs are too thin to keep the MFMA units fed. The hardware's 5.3 TB/s of HBM bandwidth becomes the real ceiling.

15What this means for optimization work

The table above is diagnostic before it's prescriptive. When a kernel shows up as unexpectedly slow in a profile, the bound classification tells you which resource to look at first — and which levers are likely to move the needle.

For memory-bound kernels, the questions are: how many times is each byte read? Can operations be fused to eliminate a round-trip through HBM? Is the access pattern coalesced? For compute-bound kernels, the questions are: what fraction of peak MFMA throughput are we achieving? Is occupancy limiting register reuse?

Decode performance on AMD Instinct hardware is almost entirely a memory-bandwidth story. The weights and the KV cache are both read from HBM on every step. Quantization (FP8, INT4) helps by shrinking what needs to be read. Continuous batching helps by amortizing those reads across more requests. Tensor parallelism distributes the reads across more HBM pools. But the ceiling is set by bandwidth, not by FLOPS — and that changes which optimizations are worth pursuing.
